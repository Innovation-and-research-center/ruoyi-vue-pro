# 通用登记节点改造说明

## 1. 改造目标

会议报告单在流程开始节点后增加“科室登记”任务，实现：

```text
保存业务数据 → 创建流程实例 → 进入登记待办 → 登记发送 → 进入下一审批节点
```

本次改造将收文专用的“来文登记”能力抽成通用登记能力，后续行政复议、行政诉讼、请假、公出等业务可以复用。

## 2. BPMN 流程配置

### 2.1 流程结构

每个业务流程在开始节点后增加一个用户任务：

```text
开始 → 科室登记 → 下一审批节点
```

### 2.2 登记节点扩展属性

登记节点建议统一配置：

```xml
<flowable:properties>
  <flowable:property name="business_node_type" value="register" />
  <flowable:property name="register_code" value="department" />
  <flowable:property name="register_submit_mode" value="complete_on_submit" />
  <flowable:property name="select_manually" value="1" />
</flowable:properties>
```

| 配置 | 作用 |
| --- | --- |
| `business_node_type=register` | 标识通用登记节点，是最关键的配置 |
| `register_code` | 登记业务分类，例如 `department` |
| `register_submit_mode=complete_on_submit` | 点击发送后完成登记任务 |
| `select_manually=1` | 允许查询并选择下一节点办理人 |

### 2.3 登记节点候选人

登记节点的候选人策略建议设置为“流程发起人”，实现谁创建、谁登记。

登记节点通常不需要配置任务组。任务组适合固定人员集合；如果登记任务配置任务组，可能会进入组内所有人的候选待办，不符合“谁创建谁登记”的业务逻辑。

旧收文登记仍保留原任务组配置的兼容逻辑，新流程不要继续依赖该方式。

### 2.4 下一审批节点

如果下一审批节点需要登记人员选择办理人，应配置：

- 候选人策略为发起人自选或手动选择。
- `select_manually=1`。
- 对应的人员、部门或用户组选择规则。

## 3. 通用后端改造

### 3.1 通用登记节点识别

通过 `BpmRegisterTaskUtils` 根据以下扩展属性识别登记节点：

```text
business_node_type=register
```

同时兼容原收文登记节点 `Activity_04ykbd0`。后续新流程不能再依赖固定 BPMN 节点 ID。

### 3.2 登记候选人计算

Flowable 创建登记任务时使用通用登记候选人逻辑，覆盖：

- 普通用户任务。
- 并行多实例任务。
- 串行多实例任务。
- 候选人校验。
- 流程节点人员解析。

新登记节点按照 BPMN 候选人策略计算，推荐设置为流程发起人；旧收文继续兼容原有任务组逻辑。

### 3.3 通用登记任务服务

`BpmRegisterTaskService` 提供两个通用能力。

创建流程后，将登记任务签收给当前用户：

```java
bpmRegisterTaskService.claim(userId, processInstanceId);
```

点击发送时，完成当前登记任务：

```java
bpmRegisterTaskService.completeOnSubmit(userId, processInstanceId, variables);
```

行政复议、行政诉讼、请假、公出等业务 Service 可以直接注入并复用。

### 3.4 查询下一节点办理人

登记节点默认允许查询下一节点，不再强依赖是否配置 `select_manually=1`；普通审批节点仍然遵循该属性，不影响已有流程。

后端虽然已经提供容错，BPMN 中仍建议明确配置 `select_manually=1`，便于阅读和维护。

## 4. 各业务模块的保存和发送逻辑

### 4.1 保存

登记类业务的“保存”不再只是保存草稿，而是：

```text
保存业务数据
→ 创建流程实例
→ 找到登记任务
→ 将登记任务签收给当前用户
→ 回写 processInstanceId
→ 更新业务办理状态
```

示例：

```java
businessMapper.insert(data);

String processInstanceId = createProcessInstance(...);
bpmRegisterTaskService.claim(userId, processInstanceId);

businessMapper.updateById(data
        .setProcessInstanceId(processInstanceId)
        .setStatus(RUNNING));
```

保存成功后，当前用户应该立即在“我的待办”看到登记任务。

### 4.2 保存后发送

点击发送时：

```text
更新业务数据
→ 复用已有 processInstanceId
→ 完成登记任务
→ 流程进入下一审批节点
```

示例：

```java
businessMapper.updateById(data);
bpmRegisterTaskService.completeOnSubmit(
        userId,
        data.getProcessInstanceId(),
        processVariables);
```

发送时不能再次创建流程，否则会产生重复流程实例。

### 4.3 未保存直接发送

如果业务允许直接发送，则按以下顺序处理：

```text
新增业务数据 → 创建流程 → 签收登记任务 → 完成登记任务
```

如果没有明确需求，建议统一采用“先保存再发送”，业务状态更清晰。

## 5. 前端改造

### 5.1 新建页面

新建页面需要：

- 保存按钮。
- 发送按钮。
- `ProcessSendDialog`。
- 保存后保留业务 ID 和流程实例 ID。
- 发送时提交下一节点办理人和流程变量。

### 5.2 管理列表修改页面

必须区分新建/登记办理和管理列表普通修改：

- 新建页面允许保存后发送。
- 从管理列表点击“修改”进入时，只显示“保存修改”。
- 管理列表修改页面不显示“发送”。
- 流程发送统一从“我的待办”进入。

会议报告单当前根据 `route.query.id` 判断是否从管理列表进入。

### 5.3 待办页面

登记任务进入待办后，发送时需要传递：

```text
processInstanceId
taskId
nextNodeAssignees
processVariables
```

查询下一节点必须基于当前任务，不能继续使用流程开始节点。

### 5.4 不要长期写死登记节点 ID

会议报告单前端目前使用了固定登记节点 ID：

```ts
const registerTaskId = 'Activity_02rawmy'
```

该方式不能直接复用于其他业务，重新绘制 BPMN 后节点 ID 也可能变化。

后续建议由后端根据 `business_node_type=register` 自动查找登记节点，前端只维护流程定义 Key：

```ts
const processDefinitionKey = 'conference_report'
```

也可以由后端返回登记节点 ID 给前端动态使用。不要为每个业务长期维护固定节点 ID。

## 6. 修改和删除操作日志

各业务管理模块统一复用：

- `BpmUpdateOperateLogService`
- `BpmDeleteOperateLogService`

修改时记录：

- 修改前数据。
- 修改后数据。
- 修改前附件。
- 修改后附件。
- 实际变更字段。

删除时记录：

- 业务类型。
- 业务 ID。
- 删除原因。

行政复议、行政诉讼、请假、公出接入时，传入对应业务名称即可。

## 8. 推荐的后续优化

下一步优先取消前端固定登记节点 ID，由后端根据登记节点扩展属性自动定位。完成后再接入行政复议、行政诉讼、请假、公出，可以减少重复代码和 BPMN 节点 ID 变化导致的问题。

## 9. 请假流程接入补充

请假登记节点配置为：

```text
business_node_type=register
register_code=leave
register_submit_mode=complete_on_submit
select_manually=1
```

请假登记后立即进入角色判断网关，创建流程和完成登记时必须携带：

```text
role_condition
days_condition3
days_condition4
```

请假开始、结束时间应按照日期和上午/下午时段直接归一化为 `08:30` 或 `13:30`，不能在原时间上重复增加小时，否则保存后再次提交会造成时间偏移。

Java 中角色编码必须使用 `equals` 比较，例如：

```java
"grade_11".equals(roleCondition)
```

不能使用 `roleCondition == "grade_11"`。
